README

skill-pick-rbnx

Robonix package for the user-facing "pick up X" skill on the Piper + Orbbec Dabai DCW grasp pipeline. The LLM-facing entry point of the whole pipeline. Owns the skill/pick/* namespace.

Catalog name: robonix.skill.pick.vertical_grasp.

What it does

Exposes a single MCP tool — robonix/skill/pick/pick(object_name) — that orchestrates three upstream services into one synchronous "pick the X" call:

                 Pilot LLM
                     │
             pick("the comb")           (MCP)
                     │
                     ▼
            ┌────────────────────────┐
            │   skill-pick-rbnx      │
            └────────┬───────────────┘
                     │
        ┌────────────┼─────────────┐
        │            │             │
        ▼            ▼             ▼
   detect_object  grasp_request  execute_grasp
  (object_detect) (grasp_pose)   (piper_moveit)
        │            │             │
        ▼            ▼             ▼
       2D bbox    grasp pose     arm motion
       + 3D ctr   + width        + gripper close

All three upstream calls are MCP HTTP (FastMCP Client). Atlas resolves the URLs at on_activate time. There is no fallback to legacy ROS service paths — this skill speaks robonix contracts only.

Capability surface

Contract Mode Transport Source / handler
robonix/skill/pick/driver rpc gRPC Driver(CMD_INIT, config_json) — lifecycle gate
robonix/skill/pick/pick rpc MCP Pick(object_name, timeout_s, max_retries) → result

Lifecycle (lazy activate)

Skills differ from primitives / services here — they do not auto-bring-up on rbnx boot:

boot:
  CMD_INIT     ── light: parse cfg, log defaults. State = INITIALIZED.
                  (No atlas resolution — upstream services may still be
                   warming up, and we don't want to deadlock boot order.)

first MCP call:
  CMD_ACTIVATE ── heavy: block up to 60 s waiting for atlas to
                  resolve the three upstream MCP endpoints. State = ACTIVE.

idle:
  CMD_DEACTIVATE ── drop endpoint cache + FastMCP client cache.
                    Re-ACTIVATE rebuilds. (Eviction policy is
                    executor's, not ours.)

Boot ordering

Skills are launched by soma stage 2 after all primitives and services. skill-pick-rbnx has no boot-time dependency on its upstreams (lazy activate covers that) — but service-object-detect-rbnx, service-grasp-pose-rbnx, and service-piper-moveit-rbnx MUST be ACTIVE before the first pick() call. If any is missing at that moment, pick() fails fast with a clear "missing dependencies" message rather than silently timing out mid-motion.

Pipeline implementation

pick_skill/atlas_bridge.py::pick(req) runs:

  1. Stage 1 — detect_object(req.object_name) over MCP. If success=False (object not in view, low confidence, etc.): short-circuit return detection_failed: <message>.
  2. Retry loop, up to req.max_retries times (default 5): a. Stage 2 — grasp_request(name, bbox_2d, object_center_3d, retry). Each retry value lets service-grasp-pose-rbnx pick a different grasp candidate. If success=False: log + continue. b. Stage 3 — execute_grasp(grasp_pose, gripper_width, exec_timeout). execute_grasp itself does the busy/idle wait on /arm/arm_status, so we do not need to. Returns once the arm hit busy → idle (success) or budget exhausted (timeout). c. If success → return immediately. d. If failure → log + next retry.
  3. After the budget or retry limit: return all_N_retries_failed; last: <message>.

Vertical-grasp three-stage motion

On the feature/vertical-grasp branch, pick() orchestrates a three-stage motion sequence via execute_grasp:

  1. pre-grasp: lift the target grasp pose by approach_dist in +z, plan + execute;
  2. grasp: descend to the target pose, close gripper;
  3. post-grasp: lift by approach_dist in +z, plan + execute.

approach_dist is configured on service-grasp-pose-rbnx.

Time budgeting

req.timeout_s is the total budget for the whole pick. Internally distributed:

  • Detection: bounded by FastMCP client timeout (~5–10 s typical).
  • Per-grasp_request: also FastMCP-bounded.
  • Per-execute_grasp: min(remaining_budget, max(8s, remaining/(retries_left+1))) — reserve some headroom for retries unless this is the last attempt.

If the caller passes timeout_s=0, we use default_timeout_s (60 s by default; tunable via deploy manifest config).

├── scripts/
│   ├── build.sh                   # rbnx codegen --mcp ONLY (no colcon!)
│   └── start.sh                   # source ROS, exec atlas_bridge
└── (no src/ — pure Python, no vendored ROS packages)

src/ is intentionally absent. Unlike primitives / services we do not vendor any ROS source: the skill talks to upstream services exclusively over MCP HTTP, and our own surfaces (Pick.srv codegen) only need Python dataclasses. Build is significantly faster (~2 s vs ~30–60 s for the moveit package).

Config (passed via Driver(CMD_INIT, config_json))

default_timeout_s:    60.0      # used when caller passes 0
default_max_retries:  5         # used when caller passes 0

Both optional. pick(timeout_s, max_retries) arguments override these per-call.

Build / run standalone

bash scripts/build.sh                                 # rbnx codegen --mcp (fast, ~2 s)
ROBONIX_ATLAS=127.0.0.1:50051 \
    bash scripts/start.sh

Failure modes

symptom cause fix
pick skill cannot find dependencies on atlas: missing [...] one of object_detect / grasp_pose / piper_moveit not ACTIVE rbnx caps to see which one's missing; check that package's log
detection_failed: object 'X' not found at confidence ≥ 0.2 object_detect genuinely does not see the object move closer; try a different object_name; test detect_object independently
grasp_pose retry N repeating without success grasp_pose returning failure (e.g. z_table wrong, bbox outside depth range) see service-grasp-pose-rbnx README
execute retry 0: timeout: arm_status never went busy piper_moveit / cpp did not pick up the GraspPose, OR /arm/arm_status not flowing check piper_ctl_rbnx ACTIVE + ros2 topic info /graspnet/grasps
pick skill not active on first call CMD_ACTIVATE failed — atlas_bridge logs the actual reason check pick_skill log; usually means upstream service down
Hangs for full timeout one of the upstream MCP servers is reachable but not responding check the slow service's log; the test harness's timeout_s is the only ceiling

Coupling with neighbours

  • Upstream service-object-detect-rbnx — provides service/perception/object_detect/detect_object MCP.
  • Upstream service-grasp-pose-rbnx — provides service/perception/grasp_pose/grasp_request MCP.
  • Upstream service-piper-moveit-rbnx — provides service/manipulation/execute_grasp MCP.
  • Indirectly upstream primitive-agilex-piper-arm-rbnx + primitive-agilex-piper-description-rbnx + primitive-agilex-piper-handeye-rbnx — pick does not talk to them, but execute_grasp does (transitively); if they are not ACTIVE, execute_grasp fails fast and pick reports it.
